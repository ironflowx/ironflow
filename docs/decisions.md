# Decisions

The decisions behind the binary and the CLI, copied from [foundation's `decisions.md`](https://github.com/ironflowx/foundation/blob/1fc3d0e38f0442151ef5701ed08e37435c27fff3/docs/decisions.md) when they moved here from foundation (ironflowx/ironflow#2). Each keeps its foundation number, and **Since** is the foundation milestone that made it. A D number these docs name that is not below is foundation's, in that file.

| # | Since | Decision | Why |
|---|---|---|---|
| D20 | 0.1 | The behaviors run under the `cucumber` crate, in an unpublished workspace crate | The feature files are the spec, run from [`behaviors/`](behaviors/README.md) |
| D23 | 0.1 | The crash test lives in an unpublished workspace crate: a child binary that owns an engine's root and a parent test that drives it over stdin and stdout. The child opens with a seed the parent chose, except where the test is of an open without one, and after `ready` prints the environment reference; the parent verifies through an engine of its own. Its stdin is one end of a socket pair: the seed goes in over it, and before any point that storing a key reaches, an open's or `create_key`'s, the child tells the parent over it the environment, the key's ID and, unless the key is a seed, its secret, so no secret passes over stdout, stderr or an argument. Two process-wide hooks, one for points and one for those keys, and `FaultPoint` live in `ironflowx-core` behind its `__fault-points`; a crate that reaches a point (today `ironflowx-cell`, `ironflowx-store` and `ironflowx-operations`) forwards its own `__fault-points` to core's and calls the hook at each named fault point, on the thread that reaches it. A published crate may turn on a dependency's `__fault-points` only from its own feature of that name, never by default or from another feature; a dev-dependency, which does not ship, may turn it on for a crate's own tests. The child's hook prints `at <point>` on its chosen pass, or on the first pass once a request arms the point, and parks that thread; the parent kills it with SIGKILL on reading the line. The 0.3 server crash fixture builds the real host once, in an isolated target directory. The host's own `__fault-points` forwards through the engine and installs the hooks when the fixture supplies its private socket. The parent supplies a seed in a private file and drives the host over loopback and through the CLI. The host reaches points around the key-file link, and the store around the recovered key's commit. For the drain and LED-14 proofs the parent can release a parked writer through the same socket, and a read reports its wait on the fold. CI checks the release workflow and the host’s ordinary build graph for the feature | The kill lands exactly at the point, by a barrier, not by timing. A process-wide hook reaches points that have no `Ledger` yet, such as during open. In core, any crate can reach a point; forwarding the one feature keeps the hook out of every build that does not ask for it by name. A later fault point adds a name and reuses the hook and the `at <point>` line; at a point before `ready` (inside an open) the parent waits for that line instead of `ready`. Told the key before the kill, the parent proves that key, not some other, accepted or refused after it; on a channel of its own, the secret reaches no log |
| D52 | 0.3 | The CLI, schemas and examples are generated at build time (the skill half is withdrawn by D82). A method without a `cli`, `summary` or valid `example` fails the build | Drift between the wire and what agents are told becomes a compile error |
| D57 | 0.3 | Settings have flags and `IRONFLOWX_*` twins; the flag wins, an empty variable is a value, unknown names warn, and there is no settings file | One precedence rule and help lists the settings |
| D58 | 0.3 | Five host settings. Limits, timeouts and drain durations are fixed | Add settings as later releases need them |
| D59 | 0.3 | The server speaks plain HTTP on loopback by default and warns for any other address; the CLI speaks `https` too; TLS in the server later | Local agents need no certificates; a remote engine sits behind a TLS proxy the CLI can reach |
| D60 | 0.3 | Before an open or a file-mode recovery that could mint, probe a write and hard link in the data directory with dummy bytes. Attempt to clean up every probe name and report any removal the OS refuses. Publish a minted or recovered key with a synced temporary file and hard link to `admin.key`, mode `0400`. Leave earlier files alone and report the undelivered key ID and recovery steps on failure | No mint after a failed probe. Publication leaves the whole key or no key at the destination and cannot clobber one already there |
| D61 | 0.3 | The CLI takes its key only from `--key-file` or `IRONFLOWX_KEY` | Picking up `admin.key` would hand every agent in the directory the admin key |
| D62 | 0.3 | Bind before open; `/ready` is 503 until open returns | An address clash changes nothing on disk; a long open reads as alive but not ready |
| D63 | 0.3 | A ledger fault signalled before close exits 8. A panic in the dev or release binary aborts the process | A restart runs the usual open and replay. An abort can precede the ledger notification |
| D64 | 0.3 | One error envelope and one exit-code table, per kind, beside `ErrorKind`, shared by every command and `describe` | An agent branches on a number, never on text |
| D65 | 0.3 | JSON only on stdout (`--help` aside), one line when piped, indented on a terminal; `json_text` values compacted; every field that is not `optional` printed | Agents first; one line holds even for data sent pretty-printed; an agent never guesses what an absent field means |
| D67 | 0.3 | `describe` reads the compiled proto and `required_scope` without an engine; `input` is the wire request and `output` is the answer printed by the CLI | An agent learns what it can do before it has an engine or a key. The CLI and other clients share a request shape |
| D68 | 0.3 | Keep keys, seeds and event data out of logs. Take a seed from a file or variable, and never take a key from a URL | These values are private and command lines, URLs and logs are copied |
| D72 | 0.3 | Signals and ledger faults drain through the slot. Stop accepting, give in-flight calls up to 10 s, drop the rest, then close the engine before the runtime | No new call is admitted during drain or after close. Already submitted work remains subject to the ledger and control plane’s commit rules |
| D77 | 0.3 | One release ships the door, the host, the client and the CLI | The binary's first users need a surface; the CLI is the one agents use |
| D79 | 0.3 | The CLI refuses an unknown field in `--json`, at any depth; the door ignores it | A mistyped `idempotency_key` would store a second event on a retry; an older engine still accepts a newer client |
| D80 | 0.3 | The host's `Operations` adapter logs each call with the presented key ID when well formed; the door logs refusals before `Operations` without a key ID | The door has no credentials dependency |
| D81 | 0.3 | Linux release archives use static musl binaries | The binaries run on clean Linux systems of the target architecture, regardless of their installed libc |
| D82 | 0.3 | No embedded skill: an agent learns the operations from `describe`. Withdraws D66 and the skill half of D52 | Embedding operational instructions in the foundation was a planning mistake ([#168](https://github.com/ironflowx/foundation/issues/168)). No release shipped one |
